# 0012. 구글 캘린더 단방향 복사 + id 매핑 (#11)

- 날짜: 2026-11-10
- 상태: 목 구현 완료, 리뷰 대기 (스펙 rev 63). 실제 구글 호출은 서비스 계정·캘린더 준비 뒤. 서비스 계정·캘린더·네트워크 없이 주입한 fetch 목(`@hsh/core/google-mock`)으로만 시험했다.

## 문제

스펙: 위키가 원본이고 구글 캘린더는 알림용 복사본(위키 -> 구글 단방향). 흐름은 "[넣기] -> 위키 수정 -> commit·push -> 캘린더 복사 -> log.md". 캘린더 실패는 위키 쓰기를 실패시키지 않는다. "구글 캘린더 이벤트 id는 별도 매핑 파일(`.sync/calendar.json`)에 둔다". 수용 기준: "같은 일정이 구글 캘린더에도 생기고, 수정·삭제도 따라간다."
포트는 `CalendarSync { upsert(e: Event); remove(id: string) }`.

## 결정

### 구조
- core `calendar/`(순수, 브라우저 안전): `toGoogleEvent`(Event -> 구글 본문), `planCalendarSync`(위키 일정 vs 매핑 -> 추가·수정·삭제), 매핑 형식(zod), `CalendarReconciler`(한 바퀴), `CalendarSyncError`.
- core/node: `GoogleCalendarSync implements CalendarSync`(서비스 계정 JWT + Calendar API v3, fetch·now·sleep 주입), `FsCalendarMappingStore`, `googleEventId`, `loadServiceAccountKey`. 시험용 가짜 서버 `google-mock.ts`(export `@hsh/core/google-mock`).
- 봇 `apps/bot/src/calendar/`: `startCalendarSync`(설정이 없으면 꺼짐), `withCalendarKick`(위키 저장소 데코레이터: 일정 변경 apply가 **성공한 뒤** 동기화를 깨움. 기다리지도, 실패를 전하지도 않음).
- 설정: `ConfigProvider.get("googleCalendar")` = `{ serviceAccountPath (GOOGLE_SERVICE_ACCOUNT_JSON), calendarId (GOOGLE_CALENDAR_ID) }`. 캘린더 id는 **config.md의 `calendarId`가 우선**, 없으면 환경 변수, 둘 다 없으면 꺼짐. 서비스 계정 파일이 없거나 형식이 틀리면 경고 한 줄만 남기고 꺼진 채로 봇은 계속 돈다.

### 동기화 방식: 매번 "지금 위키 vs 지금까지 복사한 기록" 비교 (reconcile)
- 슬랙 apply 뒤의 깨우기, 시작 15초 뒤, **5분마다** 같은 코드가 돈다. 그래서 사람이 위키를 직접 고치거나 pull로 바뀐 일정도 따라간다(apply 후킹만으로는 놓침).
- 내용 해시(본문 JSON의 sha256)가 같으면 건너뛴다. 구성원 이름이 바뀌어 설명이 달라져도 따라간다.
- 한 번에 최대 40건(나머지는 다음 바퀴), 처음 켤 때 **30일보다 옛 일정은 새로 올리지 않는다**(이미 복사한 옛 일정은 계속 따라가고 지우지 않음).
- 동시 실행은 하나로 합친다: 도는 중에 또 불리면 같은 Promise를 돌려주고, 끝난 뒤 한 번 더(최대 2번) 읽어 그 사이 변경을 따라간다.
- 실패한 건은 기록하지 않아 다음 바퀴에 다시. 인증·권한·한도 오류, 또는 3건 연속 실패면 그 바퀴는 멈춘다(느린 재시도를 건마다 반복하지 않게). 결과는 던지지 않고 `ReconcileResult`로 돌려주고 경고 로그 한 줄(종류별 수 + 힌트).
- **안전장치(대량 삭제 방지)**: 위키 events 파일에 읽기 경고가 있거나(줄을 건너뛴 것이 사라진 것으로 오해될 수 있음), 삭제가 5건 이상이면서 복사한 것의 절반을 넘으면 이번 바퀴는 삭제를 보류하고 경고한다.
- 캘린더 id를 바꾸면 기록을 새로 시작한다(이전 캘린더의 복사본은 그대로 남음. 기록에는 캘린더 id의 해시 지문만 있고 원문은 없다).

### 구글 이벤트 본문
- 종일: `start.date` + `end.date`(다음 날, exclusive). 시간 일정: `dateTime`(`YYYY-MM-DDTHH:MM:00`) + `timeZone`(config.timezone, 기본 Asia/Seoul). 끝 시각이 없거나 시작보다 이르면 시작 + 60분(자정을 넘으면 다음 날). 시작이 없는 `allDay:false`는 종일로 본다.
- 제목 = 위키 제목. 설명 = `담당: 이름들`(+ 완료면 "완료 처리된 일정") + `위키 일정 id: evt-…` + "여기서 고쳐도 위키에 반영되지 않고 다음 동기화 때 덮여요" 안내. 비공개 확장 속성 `hsh=1`, `hshId=<위키 id>`(나중에 목록으로 고아 복사본을 찾을 수 있게).
- 알림(reminders)은 지정하지 않는다: 캘린더의 기본 알림을 따른다.
- `Event.share`(공유 그룹)는 복사와 무관하다(MVP는 필드만).

### 구글 이벤트 id: **클라이언트 지정 결정적 id**(선택지 검토 결과 채택)
- 선택지 A(서버가 id를 만들고 매핑에 저장): 매핑을 잃으면 같은 일정이 중복으로 또 생긴다.
- 선택지 B(채택): `id = base32hex(sha256(가족 id + "\n" + 위키 id)[0..20])` 32자(구글 규칙: 5~1024자, 소문자 a-v·0-9). 같은 일정은 항상 같은 id라 **기록(매핑)을 잃어도 중복이 안 생기고** 덮어쓰기로 복구된다. 매핑은 "무엇을 어떤 내용으로 복사했나"의 캐시(내용 해시)가 된다.
- 동작: 수정은 `PUT events/{id}` -> 404면 `POST`(id 지정) -> 409(경합·이미 있음)면 다시 `PUT`. 삭제는 `DELETE`, 404/410은 성공 취급. 구글에서 사람이 지운 복사본을 수정하려 하면 새로 만든다.
- 구글은 지운 이벤트를 `cancelled`로 남겨 같은 id의 `POST`는 409다. 그래서 지운 뒤 같은 일정을 다시 올릴 때는 `PUT`으로 되살려야 하는데, **`PUT`이 취소된 이벤트를 되살린다는 동작은 목에서만 확인했다**(실연결 때 확인 1번).
- 남는 약점: 매핑을 잃은 채로 위키에서 지운 일정은 구글에 복사본이 남는다(비공개 속성으로 찾을 수 있으나 `CalendarSync` 포트에 목록 메서드가 없어 지금은 하지 않음).

### 인증·요청 (서비스 계정 방식, 스펙 그대로)
- JWT(RS256, `node:crypto`): `iss`=서비스 계정 이메일, `scope`=`calendar.events`(일정만. 캘린더 목록·설정은 못 건드림), `aud`=토큰 URL, 만료 1시간. 토큰 URL은 파일의 `token_uri`를 쓰지 않고 고정값(파일이 바뀌어도 다른 곳으로 키 서명이 가지 않게).
- 토큰 캐시: 만료 1분 전에 새로 받음, 동시 요청도 교환은 한 번, API가 401이면 버리고 한 번만 새로 받아 재시도.
- 요청마다 10초 제한(`AbortSignal.timeout`). 다시 시도 가능한 오류(rate_limit·server·network·timeout)는 최대 3번 지수 백오프(500ms, 1s; Retry-After 우선, 상한 30초). 오류 종류: `auth`(401·invalid_grant) · `forbidden`(403, 서비스 계정에 공유 안 함) · `rate_limit`(429, 403 rateLimitExceeded 등) · `not_found`(404·410) · `conflict`(409) · `server`(5xx) · `http`(그 밖) · `network` · `timeout` · `config`.
- **비밀값 비노출**: 오류 메시지는 고정 문구 + HTTP 상태 + 영문자 이유 코드뿐이고 원래 오류(`cause`)를 붙이지 않는다(fetch 오류 메시지에는 URL=캘린더 id가 섞일 수 있음). 이유 코드는 `^[A-Za-z_]{1,40}$`일 때만. 시험: 키(PEM)·서비스 계정 이메일·캘린더 id(원문·URL 인코딩)·토큰이 400~500·네트워크·시간 초과 오류의 message·stack·JSON·로그 어디에도 없다. 서비스 계정 JSON 읽기 실패 문구에는 파일 내용이 아니라 경로만 있다.
- 공개 상태: `AppConfig.googleCalendar`는 서버 전용. 공개 상태의 허용 목록은 그대로(`calendarId`를 내보내지 않는 기존 테스트 유지). 구글 본문에는 구성원 id 대신 이름만 나간다(가족 캘린더라 허용).

### 매핑 위치: **상태 폴더**(스펙의 위키 `.sync/calendar.json`과 다름 - 오너 확인 필요)
- `<HSH_STATE_DIR>/calendar-sync/<familyId>.json`, `{version, calendar(지문), entries: {위키 id: {googleId, hash, at}}}`. 임시 파일 + rename, 파일 권한 0600. 깨진 파일은 `.broken-<시각>`으로 옆에 치우고 새로 시작(구글 id가 결정적이라 중복 없음).
- 위키 `.sync/calendar.json`을 쓰지 않은 이유:
  1. 커밋하지 않으면 작업 트리가 더러워진다: 동기화마다 파일이 바뀌어 `pull --rebase --autostash`(봇이 연결할 1분 pull)가 매번 stash를 하고, "변경 있음" 판정에도 걸린다. `.git/info/exclude`로 무시하면 되지만 그러면 위키에 있어도 어차피 이 기계 전용이다(공유되지 않음).
  2. 커밋하면 일정이 바뀔 때마다 위키 커밋이 두 개(일정 + 동기화 기록)가 되고, push·잠금 시간이 늘고, 노트북·메인 PC에서 같은 파일을 둘이 고쳐 충돌한다.
  3. 결정적 구글 id 덕분에 매핑은 잃어도 되는 캐시라, 공유할 이유가 없다.
  4. 0007·0008이 이미 같은 방식(위키 밖 상태 폴더, 대시보드·봇 공유 `HSH_STATE_DIR`)을 쓴다. 위키에는 사람이 읽는 내용만 둔다.
- 위키에 쓰지 않으므로 `FsWikiRepository`의 쓰기 잠금(`.git/hsh-write.lock`, 0010)은 필요 없다. 쓰는 쪽은 봇 하나이고 프로세스 안은 `CalendarReconciler`가 한 번에 한 바퀴(합쳐짐)만 돈다. **나중에 대시보드 등 다른 프로세스가 같은 매핑을 쓰게 되면 그때 파일 잠금이 필요하다.** (위키에 쓰는 쪽으로 바꾸기로 하면 `commitFiles`와 같은 잠금 안에서만 쓸 것.) 시험: 통합 시험이 동기화 뒤 `git status --porcelain`이 비어 있고 위키에 `.sync`가 없음을 확인한다.

## 대안과 버리는 이유
- apply 직후에만 복사(주기 없음): 위키 직접 수정·pull·실패 후 재시도가 모두 놓친다.
- 위키 `.sync/calendar.json` 커밋: 위 2번.
- 서버가 만든 이벤트 id 저장: 매핑 유실 시 중복.
- 구글 -> 위키 반영(양방향): 스펙 비범위(위키가 원본).
- 처음부터 모든 옛 일정 복사: 첫 실행이 수백 건 호출이 된다(30일 전까지만).

## 스펙과 다른 점 / 스펙에 없어 정한 것 (오너 확인 필요)
1. **매핑을 위키 `.sync/calendar.json`이 아니라 상태 폴더에 둠.** 스펙 문구 수정 또는 위키 위치로 변경 중 선택. 위 근거로 상태 폴더를 권한다.
2. 구글 이벤트 id를 클라이언트가 정함(결정적). 스펙 "id 매핑" 문구와 의미가 달라짐(매핑이 캐시가 됨).
3. 주기 동기화(5분)를 추가함(스펙 흐름에는 apply 뒤 복사만 있음).
4. 처음 켤 때 30일보다 옛 일정은 올리지 않음, 한 바퀴 최대 40건.
5. 대량 삭제 보류(5건 이상·절반 초과, events 읽기 경고 시).
6. 캘린더 id 우선순위: config.md의 `calendarId` > `GOOGLE_CALENDAR_ID`.
7. 복사본 설명에 구성원 **이름**이 들어간다(구글 캘린더에서 보이는 사람에게 노출).
8. 스펙 .env 예시의 `GOOGLE_CALENDAR_ID`를 대체값으로 둠(config.md가 없을 때).
9. 알림 시각은 캘린더 기본 알림에 맡김(알림용 복사본이라는 목적상 실연결 때 원하는 알림을 정해야 할 수 있음).

## 필요한 환경 변수 (`.env`는 읽지 않음, `.env.example`은 오너가 추가)
- `GOOGLE_SERVICE_ACCOUNT_JSON`: 서비스 계정 키 JSON 파일 경로(예 `/home/family/secrets/gcal.json`). 없으면 복사 꺼짐.
- `GOOGLE_CALENDAR_ID`: (선택) config.md에 calendarId가 없을 때 쓸 캘린더 id.
- `HSH_STATE_DIR`: (기존) 복사 기록 위치. 위키 밖.

## 실연결 때 확인할 것 (서비스 계정·캘린더 준비 뒤)
1. 취소된(지운) 같은 id를 `PUT`으로 되살릴 수 있는지(안 되면 지울 때 id에 세대를 붙이는 방식으로).
2. 서비스 계정 이메일에 "일정 변경" 권한으로 공유한 캘린더에 `calendar.events` scope만으로 쓰기가 되는지(403이면 `forbidden` 힌트가 나온다).
3. `PUT`이 본문에 없는 필드(알림 등)를 지우는 동작이 괜찮은지.
4. 호출량: 첫 실행 40건씩 나눠 올리는 것이 한도 안인지, 5분 주기 읽기만 있는 평상시에는 구글 호출이 0인지(해시가 같으면 호출 없음).
5. 시간대 표기(`dateTime` + `timeZone`)가 서버 시각과 무관하게 맞는지.
6. 봇이 쓰는 노트북의 상태 폴더 백업(매핑을 잃었을 때 고아 복사본이 남는 약점).

## 못 한 것
- 고아 복사본(매핑 없이 위키에서 지운 일정) 정리, 구글 쪽에서 사람이 고친 것의 감지·되돌리기(다음에 해시가 바뀔 때만 덮음. 지금은 사람이 구글에서 고친 값을 우리가 알 수 없어 내용이 같으면 덮지 않는다).
- 대시보드·`/settings`에 복사 상태 표시, 슬랙 알림(실패는 봇 로그 경고만).
- 반복 일정·공유 그룹 일정의 복사.
