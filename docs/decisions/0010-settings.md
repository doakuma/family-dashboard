# 0010. /settings + 슬랙 설정 변경 (#22)

- 날짜: 2026-11-09
- 상태: 목 구현 완료, 리뷰 대기 (스펙 rev 63). 실제 슬랙 확인은 #3 토큰 뒤.

## 문제

스펙: "`/settings`(PIN 필요): 구성원 추가·색 변경·슬랙 재연결, 지역 변경", "슬랙에서도 가능: \"하늘이 색 초록으로 바꿔줘\" → 확인 후 반영 (보호자만)", "태블릿 대시보드에는 여전히 쓰기 UI를 두지 않는다. 설정은 휴대폰·PC에서만 한다."
세팅이 끝난 뒤의 위키 변경은 일정·할 일과 달리 LLM이 만드는 `Change`가 아니다. 그리고 슬랙 재연결은 세팅 마법사와 같은 "코드 -> DM -> 확인"이 필요한데, 세팅 뒤에는 마법사의 draft가 없다.

## 결정

### core
- **`SettingsChange`는 `Change`와 별개 유니언**(0004와 같은 이유: LLM·봇의 의도 추출 경로에서는 만들 수 없게). 쓰기 경로는 `WikiRepository.applySettings(familyId, change, {author})` 하나. 종류 넷: `member.add` · `member.color` · `member.slack`(slackId가 null이면 해제) · `config.region`.
- 계산은 순수 함수 `wiki/settings.ts`(`buildSettingsFiles`), 검증은 `settingsChangeSchema`(strict: 여분 필드 거부). `FsWikiRepository.applySettings`가 쓰기 큐 안에서 검증·계산 -> `commitFiles`(커밋 하나 = 바뀐 파일 + log.md) -> push. 요약은 사람이 읽는 한 줄(`하늘 색: 파랑 → 초록`, `하늘 슬랙: 연결`)이고 커밋 제목은 `[settings] …`. **슬랙 ID는 요약·log.md·커밋에 남기지 않는다**(연결/해제 여부만).
- 오류 `SettingsError`: `invalid`(422) · `not_found`(422) · `conflict`(409) · `needs_setup`(409) · `read_only`(503). 세팅 전(needsSetup)이면 거부. 이미 같은 값(같은 색·같은 지역·이미 연결/해제)도 `conflict`(빈 커밋을 만들지 않으려고).
- **기존 구성원·config 파일은 고칠 줄만 바꾼다**(`updateFrontmatterValues`): 모르는 키·주석(`<!-- -->`·`#`)·본문·CRLF는 그대로. `formatMemberFile`로 다시 쓰면 사람이 적은 필드와 본문이 사라지기 때문. 새 구성원 파일만 `formatMemberFile`.
- 구성원 추가: 마법사와 같은 `setupMemberSchema`(id 32자·`family`·Windows 예약어 거부·따옴표 감싼 이름 거부), 최대 12명, id는 대소문자 무시 유일. id를 생략하면 `suggestMemberId`(영문 slug 또는 `member-N`) - 이 함수를 대시보드에서 core로 옮겼다(마법사는 같은 이름으로 다시 내보내 import 경로 유지). 파서가 건너뛴 구성원 파일의 이름도 쓰인 것으로 본다.
- 색: 고를 수 있는 색은 기존 목록(`PICKABLE_COLORS`, gray 제외)이고, 한국어 견본 이름(`COLOR_LABELS`)과 함께 core `member-colors.ts`로 옮겼다(대시보드 색 고르기와 슬랙 명령이 같은 표). **다른 구성원과 같은 색은 허용**(마법사도 막지 않는다).
- `ConnectScope`에 `"settings"` 추가(0007이 예고). 범위가 다르면 서로의 코드를 지우거나 같은 슬랙 계정 중복 검사에 얽히지 않는다(`memberKey` = 위키 구성원 id).

### 대시보드 `/settings`와 `POST /api/settings`
- 화면: 휴대폰 표면, 마법사의 카드·목록·`Button`·`SwatchGroup`·`TextField`·`RegionOptions`(1단계에서 뽑은 지역 선택)를 그대로 쓴다. 새 CSS는 줄 안 배치 몇 개뿐(색 없음, 하드코딩 색 검사 폴더에 추가). 구역 셋(구성원 · 슬랙 연결 · 지역)은 **독립 저장**이고 한 번에 하나. 접근성: label, `aria-invalid/describedby`(Field), 오류 `role=alert`, 성공 `role=status aria-live`, 터치 48px(e2e가 검사), 입력 16px(phone 표면), 저장 뒤 포커스를 눌렀던 자리로.
- API는 엔드포인트 하나 + `kind`(`member.add` · `member.color` · `region` · `slack.code` · `slack.status` · `slack.save` · `slack.unlink`). 방어는 setup과 같은 공통 관문(`guardJson`): 출처 403 -> 세션 401 -> 본문(411·413·415·400) -> zod 422 -> 도메인 409/503. 본문 상한 2KB. 쓰기 저장소는 setup과 같은 방식(`getWikiWriter`), author는 `settings`.
- **지역은 지역표 키만 받고** 격자·코드는 서버가 채운다(클라이언트가 코드를 위조해 보낼 수 없음). 마법사의 "직접 입력"은 가져오지 않았다.
- **슬랙 재연결(코드 -> DM -> 폴링 -> 저장)**: `slack.code`가 `settings` 범위 코드를 발급(이름·역할은 위키에서 읽음) -> 본인이 봇에게 `연결 123456` -> 화면이 3초 폴링(`slack.status`, 마법사의 `useConnectStates` 재사용: 가져오는 함수만 주입) -> 확인되면 [연결 반영] -> `slack.save`가 **서버에서** 연결 기록의 slackId를 꺼내 `member.slack`으로 쓰고 코드를 폐기. 더 단순한 모양을 찾지 못했다: "DM이 오면 봇이 바로 위키에 쓰기"는 봇이 PIN 없이 설정 쓰기를 하게 되어 권한(PIN) 경계가 무너진다. 그래서 PIN 세션이 있는 화면이 마지막 저장을 한다. 코드에 든 구성원 id와 요청의 id가 같아야 하고(다른 구성원 몫의 코드 거부), 범위가 `settings`여야 한다.
- 슬랙 ID는 화면·API 응답 어디에도 없다. 구성원 목록은 `connected: boolean`만 준다(`toSettingsView`가 허용 목록으로 골라 담음).
- `/settings`는 PIN 세션(via=pin)이 있으면 열리고, 마법사 세션(via=setup)도 기존대로 연다(0002 그대로: 같은 PIN을 거침. 세팅 전에는 `needs_setup`으로 쓰기가 거부된다. 세팅을 끝내면 완료한 브라우저의 쿠키만 지워지고, 그 밖의 setup 세션은 서명 쿠키라 서버에서 폐기할 수 없어 30분 만료를 기다린다). 세팅 전 위키는 "첫 세팅이 끝나지 않았어요" 안내만 보인다. 내부망 제한은 기존 그대로(proxy).

### 봇: 슬랙 색 변경 고정 명령 (`apps/bot/src/settings/`)
- `index.ts`에서 연결 코드 처리기 다음, Conversation(LLM)보다 먼저 가로챈다. **LLM 호출 없음.**
- 문장 모양(`parse.ts`, 정규식): `<이름>(이|가|의)? 색(깔)?(을|를)? <색>(으)?로 (좀)? 바꿔(줘|주세요|줄래|봐)?` 와 짧은 꼴 `<이름> 색 <색>`(짧은 꼴은 **아는 색일 때만** 명령으로 본다). 모양이 안 맞으면 위키도 읽지 않고 기존 흐름으로 넘긴다. 오탐 방지 테스트: "하늘이 색종이 사야 돼", "초록색 크레파스 사기", "하늘이 색 종이 사야 돼", "오늘 하늘 색이 예쁘다" 등.
- 대상: 위키 구성원의 이름·id(대소문자 무시)로 정확히 -> 없으면 이름 부분 일치(두 글자 이상) -> `@멘션`은 슬랙 ID. 끝의 조사(이·가·의)는 뗀다. **구성원이 아닌 것에 대한 말("벽 색 초록으로 바꿔줘")은 가로채지 않는다.** 여럿이면 후보를 말하고 끝(버튼 없음). 모르는 색("빨강")이면 가능한 색 목록 안내.
- 권한: `permissionFor`/`canWrite`, 보호자만. 아이·미등록은 #21과 같은 방식의 안내(설정용 문구 1개 추가: "아이 계정은 설정을 바꿀 수 없어요. 보호자에게 부탁해 주세요." 미등록은 #21 문구 재사용). 권한 안내가 색·이름 안내보다 먼저.
- 확인: 카드 `하늘 색을 파랑 → 초록으로 바꿀까요?` + [바꾸기][취소]. 이미 같은 색이면 버튼 없이 "하늘 색은 이미 초록이에요." 요청 보관은 `SettingsPendingStore`(flow/PendingStore와 같은 규칙: 버튼 값에는 요청 id만(`s_` 머리말로 어느 쪽 요청인지 가림), 상태 전이로 두 번 눌러도 한 번, 요청자만 누름, 24시간 만료, 메모리). LLM의 `Change`를 담는 flow/PendingStore와 담는 것이 달라 따로 뒀다.
- 버튼 시점: 위키를 다시 읽어 권한·구성원 존재·현재 색을 재판정(#21 규칙). 읽기 실패는 닫지 않고 되돌림("잠시 뒤 다시 눌러 주세요"), 권한 없음은 닫고 안내, 그 사이 이미 같은 색이면 쓰지 않음, 쓰기 실패는 [다시 시도][취소]. 반영은 `applySettings(member.color)`. **작성자는 `slack:<구성원 이름>`**(슬랙 ID는 GitHub로 가는 위키에 남기지 않는다. 이름의 `<>`·줄바꿈은 뺌). 채널·DM 모두 같은 곳에 답한다.
- 설정 코드 DM: `ConnectHandler`는 claim 결과의 범위로 문구를 고른다("설정 화면에서 '연결 반영'을 눌러야 저장돼요"). 채널에 올라온 settings 코드도 기존대로 무효화된다.

### 리뷰 반영: 프로세스 간 쓰기 잠금
- 대시보드와 봇이 같은 `WIKI_REPO_PATH`에 쓰는데 `FsWikiRepository`의 큐는 프로세스 안에서만 직렬화한다. 그래서 log.md 줄 유실, git `index.lock` 충돌 뒤 rollback이 상대 커밋의 변경을 지움, 봇의 1분 `pull --rebase --autostash`가 대시보드 쓰기와 겹치는 일이 가능했다.
- 쓰기 큐의 모든 작업(`apply`·`applySetup`·`applySettings`·`pull`)이 **파일 잠금 `.git/hsh-write.lock`** 안에서 돈다. 0007과 같은 방식: 임시 파일에 `{pid, token, at}`을 쓰고 `link(2)`로 배타 생성(이미 있으면 EEXIST = 남이 쓰는 중). 기다리며 50ms 간격 재시도, 상한 30초(`lockWaitMs`) 넘으면 `WikiLockError`(원인과 잠금 경로를 담은 문구, 파일은 건드리지 않음). 풀 때는 내 token일 때만 지운다.
- 오래된 잠금 정리(재리뷰 반영): **주인 pid가 없거나(`kill(pid,0)`) 내용이 깨진 잠금만** 지우기 직전에 다시 읽어 같은 잠금일 때만 지우고 경고를 남긴다. 주인이 살아 있으면 오래돼도 치우지 않는다(느린 push 중일 수 있고, 빼앗으면 동시 쓰기가 된다). 30분(`lockStaleMs`)이 넘게 쥐고 있으면 경고 로그만 한 번 남긴다.
- 네트워크 git 명령(`push`·`pull`)은 제한 시간 90초(`gitNetworkTimeoutMs`)와 `GIT_TERMINAL_PROMPT=0`로 돈다. push 시간 초과는 커밋을 유지한 채 `synced:false` + `syncError`("시간 초과"), pull 시간 초과는 되돌리고 오류. 그래서 잠금은 최대 약 90초 + 로컬 작업 시간만 쥔다.
- `WikiLockError` 메시지는 "다른 곳에서 저장 중이에요. 잠시 뒤 다시 해 주세요" 고정이고 경로는 로그에만 남긴다(슬랙 카드 '원인:'·화면에 경로가 나가지 않게). 설정 API는 이를 503(`busy`)로 돌려준다. 잠금 파일이 없는데 `link`가 거부되면(FAT·일부 네트워크 드라이브) 기다리지 않고 "하드 링크를 지원하지 않아…" 오류로 바로 실패한다. 두 프로세스가 동시에 정리하는 아주 좁은 경합은 남는다(받아들임: 정리 직후 한쪽이 새로 잠금을 얻는 사이에 다른 쪽이 옛 내용을 들고 지우는 경우).
- Windows: `link`가 EPERM/EBUSY면 한 번 다시 시도하고 그래도 안 되면 "남이 쓰는 중"으로 보고 기다린다. NTFS(하드 링크 지원)가 필요하다(0007과 같음). `kill(pid,0)`은 Windows에서도 동작한다. 잠금은 같은 기계·같은 PID 공간의 프로세스만 가정한다(대시보드와 봇을 컨테이너로 나눠 같은 볼륨을 공유하는 구성은 금지: pid 확인이 틀린다. 네트워크 드라이브 공유 위키도 지원하지 않음). 봇의 1분 pull 주기는 아직 연결되지 않았고, 연결할 때는 `pull()`(같은 잠금 안)만 쓴다.
- 테스트: 저장소 인스턴스 둘로 8건 동시 쓰기(log 줄·파일 줄·커밋 수 전부 맞음), 잠금 대기 후 쓰기, 대기 상한 오류, 오래됨·죽은 pid·깨진 잠금 정리, 실패해도 잠금 해제, pull도 잠금 안.
- 같은 리뷰의 작은 수정: 성공 문구의 동기화 경고는 `syncError`가 있을 때만(마법사와 같다), `updateFrontmatterValues`는 같은 키가 여러 줄이면 읽을 때 쓰이는 마지막 줄을 고친다, 연결 코드 DM 실패 안내는 범위에 따라 "설정 화면"/"세팅 화면", "(으)로" 조사는 core `euro()`로, 작성자 예시는 `slack:<이름>`.

## 대안과 버리는 이유
- `Change` 유니언에 설정 종류 추가: LLM 출력 스키마·프롬프트에 노출되어 "색 바꿔줘"가 의도 추출을 거치게 된다. 고정 명령은 코드가 직접 처리한다는 스펙 표와 어긋난다.
- 슬랙 연결 코드를 받으면 봇이 위키에 바로 반영: 봇이 PIN 없이 설정을 쓰게 된다(위 설명).
- `formatMemberFile`로 구성원 파일 전체를 다시 쓰기: 모르는 필드와 본문이 사라진다.
- 구성원 id를 클라이언트가 정하기: 서버가 생성 규칙대로 만든다(충돌은 쓰기 큐 안에서 검사).
- 지역 코드를 클라이언트가 보내기: 위조 가능. 키만 받는다.
- 상태 코드 404(not_found): 지정된 401/409/415/422/503 안에서 처리하려고 422로 뒀다.

## 하지 않음 (스펙에 없음)
- 구성원 삭제·역할 변경·이름 변경·생일 변경(구성원 추가에도 생일 입력 없음: 생일은 기념일과 짝이라 슬랙 기념일 추가로).
- 스킨·캐릭터 고르기(#30), 가족 이름·시간대·캘린더 ID 변경, 지역 직접 입력.
- 슬랙 ID 직접 입력(항상 코드로).

## 스펙과 다른 점 / 스펙에 없어 정한 것 (오너 확인 필요)
1. **포트 `WikiRepository`에 `applySettings` 추가** + `SettingsChange` 타입: 스펙 "인터페이스" 절 갱신 필요(applySetup과 같은 지위의 내부 메서드).
2. 슬랙 재연결을 **화면의 [연결 반영] 버튼으로 저장**(자동 반영 아님). 이유는 위 "슬랙 재연결".
3. 구성원 추가에 **생일 없음**, 삭제·역할·이름 변경 없음.
4. 다른 구성원과 **같은 색 허용**(마법사와 같다). "노랑·녹색·파란" 말씨를 호박·초록·파랑으로 받는다(빨강·주황·하늘 등은 모르는 색 안내: "하늘"은 구성원 이름과 헷갈려서 뺌).
5. 짧은 꼴("하늘 색 초록")도 명령으로 받는다. 구성원이 아닌 대상은 LLM 흐름으로 넘긴다. 이름 부분 일치(김민준 <- "민준") 허용.
6. 작성자 표기: 대시보드 `settings`, 슬랙 `slack:<구성원 이름>`(일정·할 일은 기존대로 `slack`).
7. 마법사 세션(via=setup)도 `/settings`를 연다(기존 유지). 세팅 전에는 쓰기 거부.
8. 보호자가 자기 슬랙 연결을 풀거나 유일한 보호자의 연결을 풀 수 있다(슬랙으로 쓸 수 없게 되지만 /settings에서 복구 가능). 막지 않았다.
9. 나가기는 기존대로 첫 화면(`/`)으로 이동한다.
10. 실패한 요청(메모리)은 봇 재시작 시 사라진다(#9와 같음).

## 못 한 것 / 남은 문제
- 실제 슬랙 DM·버튼 동작은 #3 토큰 뒤 확인. 필요 값: `SLACK_BOT_TOKEN`, `SLACK_APP_TOKEN`, `SLACK_FAMILY_CHANNEL`, `WIKI_REPO_PATH`, `HSH_STATE_DIR`(대시보드·봇 같은 값), `ADMIN_PIN_HASH`, `DASHBOARD_BASE_URL`.
- 태블릿 화면은 폴링(60초)으로 바뀐 색·지역을 반영한다(즉시 아님). 지역 변경 직후 날씨는 다음 갱신 때 새 지역으로 바뀐다.
- 구글 캘린더(#11) 복사본에는 설정 변경이 영향이 없다(일정만 복사).
